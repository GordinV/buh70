Дата: 2026-11-15. Статус: **реализовано в коде и тестах (ai_task: 175 тестов, бэкенд: 4 набора), SQL не выкатывался в БД** — см. раздел 9.

## 1. Что случилось

| 07:00 | `getEarved` | SUCCESS, лог 8563297 |
| 07:30 | `check_asutus` | SUCCESS |

`import_earved` формально не падал. Упал только `sendFinBitReport`.

## 2. Причина

Импорт не создал ни одного нового счёта, а ситуация «нечего отправлять» считается ошибкой.

1. `routes/raama/sendFinBitReport.js:438` — при нуле строк из `docs.get_arve_kinnitaja` лог закрывается со статусом `failed`. Того же требует `prompt` в `sendFinBitReport/config.json` («если массив result пуст — FAILED»).
2. `sql/ou/get_arve_kinnitaja.sql` ищет id документов по тексту `id: N` в ответе импорта. При нуле импортированных счетов ответ — `Imporditud 0 arvet (leitud: N)`, id в нём нет.
3. Резервная ветка по номерам счетов требует, чтобы документ был создан в окне ±30 минут. Уже существующие счета `docs.sp_loe_earved` пропускает молча (`continue`, строка 115), но их номера остаются в `invoiceNumbers`, поэтому совпадений нет.
4. Ошибка детерминированная, но оркестратор повторяет любой `failed`: 3 попытки с шагом тика 30 минут, после чего весь суточный цикл получает `FAILED`.

Гипотеза выведена из кода; содержимое лога 8563304 не проверялось. Проверка перед началом работ:

```sql
SELECT id, propertis ->> 'response' AS response,
       propertis -> 'result' ->> 'totalFetched'  AS fetched,
       propertis -> 'result' ->> 'totalImported' AS imported,
       propertis -> 'result' ->> 'totalSkipped'  AS skipped
FROM ou.logs WHERE id IN (8563297, 8563304);

SELECT * FROM docs.get_arve_kinnitaja(8563304);
```

Если `imported > 0`, а функция возвращает 0 строк, причина другая (разбор `id: N` или соединения внутри функции) — пункт И2 её всё равно закрывает, но пункт И1 сам по себе сбой не устранит.

## 4. Изменения

Обозначения слоёв: **SQL** — PostgreSQL, **BE** — бэкенд `buh70` (`routes/`, Node.js < 14, без `?.` и `??`), **AI** — микросервис `ai_task` (TypeScript).

### И1. «Нет новых счетов» — успех без рассылки

Решение принимает бэкенд: он один видит и результат импорта, и результат выборки получателей. Вариант «оркестратор ставит `SKIPPED` до запуска» не выбран — пришлось бы хранить счётчики импорта в состоянии оркестратора.

**BE `routes/raama/sendFinBitReport.js`** (`runCalculationInBackground` и `executeReport`):

| Импортировано документов (`result.imported` лога импорта) | Строк получателей | Статус лога | `retryable` | `response` |
|---|---|---|---|---|
| 0 | 0 | `success` | — | `Uusi arveid ei imporditud, teavitusi ei saadetud` |
| > 0 | 0 | `failed` | `false` | `Imporditud N arvet, kuid saajaid ei leitud` |
| > 0 | > 0, все письма ушли | `success` | — | как сейчас |
| > 0 | > 0, часть не ушла | `failed` | `true` | перечень адресов и ошибок |
| лог импорта не найден или не того flow | — | `failed` | `false` | `Impordi logi ei leitud` |

- Количество импортированных документов читается из лога импорта по переданному `logId` до вызова `get_arve_kinnitaja`.
- В `propertis` лога рассылки дополнительно пишутся `source_log_id` (id лога импорта) и `no_op: true` для первого случая.
- `result` остаётся массивом результатов отправки (пустым при `no_op`), чтобы не ломать `inspectLogExecutionResult`.

**AI `sendFinBitReport/agent.ts`**: добавить `manifest.enrichReportStep` — эстонское резюме для отчёта: `Uusi arveid ei olnud` / `Saadetud N teavitust (M arvet)` / `Saatmata K teavitust: …`.

### И3. Политика повторов и идемпотентность рассылки

**BE**:
- `routes/raama/sendFinBitReport.js`, `routes/raama/importEarved.js` (и общий `endLog` в `getEarvedFromFinBit.js`): при `failed` писать в `propertis` ключ `retryable` (`true` / `false`).
  - `true`: SMTP-таймауты, сетевые ошибки, обрыв соединения с БД.
  - `false`: нет данных, нет или неверный `logId`, нет прав (`Puudub õigused`), ошибки справочников.
- `routes/ou/readLog.js`: вернуть в выборке `(propertis ->> 'retryable')::boolean as retryable` и `propertis ->> 'source_log_id'`.
- `routes/raama/sendFinBitReport.js`: перед отправкой собрать адреса с `success: true` из предыдущих логов `sendFinBitReport` с тем же `source_log_id` и исключить их. В `result` такие адреса отмечать `{email, success: true, already_sent: true}`. Итог — `success`, если каждому получателю письмо ушло сейчас или раньше.

**AI**:
- `logs_watcher/schemas.ts`: необязательное поле `retryable` в записи лога; `logs_watcher/agent.ts` (`checkTaskStatus`, `watchTaskUntilDone`) пробрасывает его в результат.
- `orchestrator/orchestrator.agent.ts` (ветка «задача завершилась с ошибкой»): при `retryable === false` сразу `FAILED` с событием `TASK_FAILED_NON_RETRYABLE`, без повторов. Если поля нет — поведение прежнее (повтор до `max_attempts`), старые агенты не затрагиваются.

### И6. Изоляция ошибок по счетам в импорте

**SQL `sql/raama/docs.sp_loe_earved.sql`**:
- Тело цикла по счетам обернуть в `BEGIN … EXCEPTION WHEN OTHERS THEN … END` (подтранзакция на счёт). При ошибке — запись в `errors` (`number`, `asutusid`, `SQLERRM`) и переход к следующему счёту.
- В обработчике сбрасывать `l_doc_details` и `l_json_doc`, иначе строки ошибочного счёта попадут в следующий.
- Проверки, общие для всего батча (права пользователя, пустой массив), остаются до цикла и по-прежнему прерывают вызов.

**BE `routes/raama/importEarved.js`** — статус лога импорта:

| Импортировано | Ошибок | Статус | `retryable` |
|---|---|---|---|
| любое | 0 | `success` | — |
| > 0 | > 0 | `success` (частичный успех, `errors` в `result`) | — |
| 0 | > 0 | `failed` | `false` |
| исключение батча (БД недоступна и т.п.) | — | `failed` | `true` |

При частичном успехе `sendFinBitReport` запускается и рассылает уведомления по импортированным счетам. Счета с ошибкой подтянутся при следующей выкачке (окно `date_query_from`), как и пропущенные из-за отсутствующего контр-агента.

**AI `logs_watcher/agent.ts`**: убедиться, что `inspectLogExecutionResult` не считает непустой `result.errors` при `status: success` сбоем (сейчас проверяются только `result.error` и `result.success === false` — менять не нужно, закрепить тестом).

Следствие: в штатном режиме отчёт уходит в 08:00 с результатами сегодняшней цепочки. Если цепочка задержалась из-за повторов, отчёт ждёт её до 09:00 и уходит с тем, что есть.

### Принудительный запуск (`--task <ключ>`): текущее поведение, без изменений

- Указанная задача и все зависящие от неё (кроме `reporter`) сбрасываются в `PENDING`; на этом тике запускается только указанная, остальные — на следующих обычных тиках.
- Расписание по времени для указанной задачи не проверяется. Зависимости проверяются: все предшественники должны быть `SUCCESS`, иначе `WAIT` (или `SKIP`, если предшественник `FAILED`/`SKIPPED`).
- Предшественники не перезапускаются: `--task import_earved` разбирает уже выкачанный лог `getEarved`. Для свежей выкачки запускать `--task getEarved` — тогда каскадно пройдёт вся цепочка, включая платный `inforegister`.
- Если суточный цикл уже закрыт (`COMPLETED`/`FAILED`), `--task` без `--force` не запускает задачу: тик завершается ожиданием `next_scheduled_run`. Нужно `--task <ключ> --force`.
- До этапов 1–3: повторный `--task import_earved` в тот же день создаёт 0 новых счетов, и `sendFinBitReport` снова завершится `FAILED`. После этапов 1–3 — `success` без рассылки.

## 5. Пункт 5: к чему приведёт привязка к `log_id`

Сейчас оркестратор спрашивает «каков статус последней записи flow X у пользователя Y». После изменения — «каков статус записи N, которую я сам запустил».

**Что улучшится**
- Статус относится ровно к запущенному экземпляру. Чужой запуск того же flow (ручной вызов, старый неагентский путь `getEarvedFromFinBit`, который тоже пишет `docs.sp_loe_earved`) больше не будет принят за результат задачи оркестратора.
- Исчезает класс ложных `SUCCESS`/`FAILED`: «увидели вчерашнюю или постороннюю запись и решили, что наша задача завершилась».
- `reporter` показывает запуск текущего цикла, а не «последний за 24 часа».
- Данные между шагами цепочки (`logId` родителя) и контроль статуса используют один и тот же идентификатор.

**Что изменится в поведении и требует внимания**
1. **Ручной перезапуск перестанет «засчитываться» автоматически.** Сейчас, если задача упала и человек перезапустил её вручную, оркестратор на следующем тике видит успешную последнюю запись и ставит `SUCCESS`. После изменения он будет смотреть только на свою запись и уйдёт в повтор. Поэтому в И5 добавлена сверка перед повтором: более поздний успешный запуск того же flow за сегодня принимается, повтор не делается.
2. **Эндпоинт обязан возвращать «правильный» `log_id`.** Если эндпоинт возвращает id одной записи, а статус пишет в другую, задача навсегда останется `RUNNING` до watchdog (12 часов) либо уйдёт в повтор как «не стартовала». Известный пример: `docs.sp_loe_earved` создаёт собственную запись в `ou.logs` без `flow` — она оркестратору не видна и не должна использоваться. Отсюда обязательный аудит всех `/task/*` до включения.
3. **Запись должна читаться под тем же `user_id` и `flow`.** `read_log` с `log_id` игнорирует окно по времени, но фильтр по пользователю и flow остаётся. Если процедура пишет лог под другим пользователем (подмена на «робота»), запись не найдётся → `not_started` → повтор. Сегодня эта проблема тоже есть, но маскируется поиском «последней записи».
4. **Нужен запасной путь без `log_id`.** `dispatch` может вернуть `null`, состояние может быть потеряно, запуск может быть «подхвачен» через `guardAgainstDuplicate` без id. Во всех этих случаях остаётся прежний поиск по flow.
5. **Сверка с логами остаётся по flow.** `checkTaskAlreadyRunToday` ищет запуски, сделанные не оркестратором, — у них нет известного `log_id` по определению. Найденный id записывается в состояние, дальше контроль идёт по нему.
6. **Тесты.** Моки `readTaskLog` в `orchestrator.test.ts`, `logs_watcher.test.ts`, `reporter.test.ts` сейчас отдают «последнюю запись»; их нужно дополнить сценариями с `log_id` и с посторонней более поздней записью того же flow.

**Риск внедрения**: средний. Изменение затрагивает контроль всех агентов, а не только цепочки FinBit. Включать после аудита из пункта 2 и отдельно от остальных пунктов (см. порядок работ).

1. **Аудит И5 выполнен**: все `/task/*` возвращают `log_id` записи, которую сами закрывают через `endLog`, с тем же `flow` и `user_id`. Исключений не найдено.
